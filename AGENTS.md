# AGENTS.md — PELENG 3D Tracker

> Обязательные рабочие правила для Codex во всём репозитории.
> **Приоритет:** запрос пользователя и согласованные решения → этот файл → относящиеся к задаче разделы `docs/PROJECT_SPEC.md` → существующие соглашения кода. Если требования конфликтуют — уточни, не выбирай молча.

## 1. Задача проекта

Построить реальную стереосистему: **MacBook = камера + обработка + интерфейс; iPhone = отдельное iOS-приложение со второй камерой**. Реальные кадры с двух устройств → сопряжение/синхронизация → калибровка → обнаружение объекта → триангуляция → X/Y/Z, траектория, запись и экспорт. Следующий этап — внешние USB/IP/промышленные камеры через интерфейс источника кадров **без переписывания математического ядра**.

Синтетический тест не доказывает работу реальных камер. Не подменяй измерения, FPS, координаты, графики, соединение или калибровку заготовками; не используй «демо» как основной сценарий. Рабочие функции и честное состояние системы важнее эффектной картинки. Детальное ТЗ: `docs/PROJECT_SPEC.md`.

## 2. Перед КАЖДОЙ новой задачей — проверка понимания

1. Прочитай запрос, уже подтверждённые решения и **только минимально нужный код**. Перед изменениями назови одним-двумя предложениями, **что именно нужно изменить, а что сохранить**.
2. Если есть решение, от которого меняется результат, задай **1–3 точных вопроса одним сообщением**: ожидаемое поведение, границы работы, приёмочные критерии, ограничения устройств/UX/данных. Если значимых развилок больше — задай необходимое число без искусственного лимита. Предлагай разумный вариант с кратким объяснением.
3. **Обязательно получи ответ ДО значимых изменений**, когда выбор касается архитектуры Mac–iPhone, протокола/временных меток, точности/калибровки, безопасности, приватности, новых больших зависимостей, удаления данных, несовместимых API, UX-сценария или существенного расширения задачи. Молчание не означает согласие.
4. Если задача **однозначна** и пользователь уже дал всё необходимое — не выдумывай вопросы ради формальности: кратко обозначь понимание и начинай. Если пользователь попросил подтвердить *каждую* задачу — спроси подтверждение и для однозначной. **Никогда не переспрашивай то, что уже известно.**
5. После ответов зафиксируй кратко: **цель → границы → критерий готовности**. Затем работай самостоятельно в пределах согласованного: не спрашивай разрешения на каждую команду/файл. Новое существенное решение — снова согласование. Не блокируй независимые безопасные задачи из-за одного нерешённого вопроса.

**Пример:** «Добавить поддержку внешней камеры» — спроси, какой тип/модель камеры обязателен и должна ли она заменять iPhone или работать параллельно; не переписывай стек исходя из собственной догадки.

## 3. Минимальные токены, максимальная точность

- **Узкий контекст:** `git status` → `rg` по символу/поведению → нужные функции и их вызовы → соседние тесты. Не перечитывай весь репозиторий и это полное ТЗ при каждой мелкой задаче. Расширяй поиск только по обнаруженным зависимостям.
- **Короткий рабочий план:** для сложной задачи 3–5 шагов; для локальной — без длинного плана. Не повторяй вводные, историю проекта, рассуждения и большие листинги кода в ответах.
- **Reuse first:** сначала существующие функции, типы, алгоритмы и библиотеки. Не делай параллельную реализацию того, что уже работает. Внешний поиск — только при нехватке фактов, изменившихся API или реальном техническом блокере; предпочитай официальную документацию.
- **Гипотеза → проверка → точечное исправление:** не устраивай серию слепых попыток. После ошибки смотри конкретный лог; не повторяй без изменений неудавшуюся команду.
- **Экономь токены на шуме, НЕ на качестве:** адресный вывод и краткие сводки допустимы; пропускать тесты, обработку ошибок, безопасность и проверку совместимости нельзя.
- Не добавляй незаказанные функции, масштабный рефакторинг, повсеместное форматирование, обновление всего стека и лишние зависимости «заодно».

## 4. Точечные правки, но корректно во ВСЁМ проекте

1. Перед правкой установи **источник проблемы** и цепочку зависимостей: Mac UI → источник кадра → транспорт → iPhone → Python/OpenCV/математика → экспорт, если это относится к задаче.
2. Меняй **минимальный достаточный набор файлов и строк**. Сохраняй рабочую структуру, API, формат сообщений и поведение соседних функций. **Запрещено переписывать большие модули или весь проект ради локального запроса**, кроме случаев явно согласованной необходимости.
3. Если меняется общий контракт (кадр, время, калибровка, API), **точечно обнови обе стороны и все реальные места использования**. Малый diff не оправдывает сломанную другую платформу.
4. Для бага — воспроизведение и регрессионная проверка по возможности. Для нового поведения — позитивный и основные негативные сценарии. Сначала тесты изменённого участка, затем релевантные интеграционные тесты/сборки.
5. Проверь `git diff --check`, `git diff --stat` и содержимое diff. Убери случайные изменения. **Не затирай чужие незакоммиченные правки; не выполняй удаление или необратимые миграции без разрешения.**
6. Не скрывай ошибки, не отключай падающие тесты, не рисуй поддельные статусы, не отмечай непроверенное как готовое.

**Пример:** пользователь просит поправить отображение FPS → найти расчёт и привязку UI, исправить их и протестировать. **Не трогать** калибровку, захват и 3D-реконструктор без доказанной причинной связи.

## 5. Неприкосновенные инженерные требования

- **Настоящий iOS-захват** (Swift/SwiftUI, AVFoundation) и настоящий поток Mac, не запись из файла. Продуманная передача кадров и метаданных, проверка сетевого соединения, восстановление после обрыва.
- Временные метки разных устройств **не сравниваются напрямую без оценки смещения часов**; программная Wi-Fi синхронизация не равна аппаратной. При некачественной синхронизации/калибровке нельзя выдавать уверенную 3D-позицию.
- Геометрия: документированные системы координат, единицы, параметры объективов, стереокалибровка, проверка ошибки репроекции. Не смешивать тестовую RMSE с измеренной точностью в реальности.
- Расширяемость: источники камер через адаптеры; Python-ядро сохранить при его корректности; не дублировать алгоритм отдельно для двух приложений без причины.
- Интерфейс: честные статусы, настоящие действия кнопок, понятные ошибки, живые превью, показатели качества, экспорт; чистый инженерный стиль.
- Безопасность: не отправлять видео в облако без согласия; не включать секреты, ключи, приватные записи в репозиторий и архив.
- Операционная документация: установка Mac/iPhone, подпись iOS, калибровка, размещение телефона **без штатива**, протокол, диагностика, реальные результаты испытаний.

## 6. Проверки и отчёт агента

Для законченной задачи кратко сообщи: **изменённые файлы → что стало работать → выполненные команды/результаты → что не было проверено физически → следующий блокер (если есть)**. Не утверждай сборку/работу на устройствах, если их у агента не было. Не называй задачу завершённой при известных критичных дефектах.

Проверяй соответствующий раздел `docs/PROJECT_SPEC.md` **только при реализации этой области**. Если в проекте есть документация с актуальнее подтверждёнными данными, учитывай её; при конфликте важных требований спроси пользователя. Поддерживай документацию и `docs/TEST_REPORT.md` по факту, без несуществующих команд.

## 7. Итоговая поставка проекта

**После реализации проекта**, по согласованному объёму, упакуй исходники macOS/iOS, математическое ядро, Xcode-проекты, инструкции, тесты и фактический отчёт в **один ZIP**. Исключи `.git`, `.venv`, `node_modules`, `__pycache__`, ключи, личные кадры и временные сборки. Проверь список файлов, распаковку и по возможности сборку из чистой копии. В итоговом ответе дай ссылку на ZIP и настоящие инструкции установки; отдельно назови шаги, которые может выполнить только пользователь на его Mac/iPhone.

**Критерий успеха:** небольшой понятный diff на каждую задачу, согласованные решения и реальное проверяемое поведение всей системы, а не длинный ответ, красивый мокап или серия переписываний.
